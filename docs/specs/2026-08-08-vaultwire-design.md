# vaultwire — дизайн

Дата: 2026-08-08. Статус: утверждён к реализации.

Двусторонняя синхронизация хранилищ Obsidian между участниками команды через собственный сервер, со сквозным шифрованием на клиенте. Сервер не может прочитать ни содержимое заметок, ни их имена, ни структуру папок.

---

## 1. Модель

**Пространство (space)** — набор файлов, который синхронизируется между участниками. У пространства есть соль, верификатор пароля, эпоха ключа и монотонный счётчик изменений.

**Устройство (device)** — один установленный плагин у одного человека. Имеет собственный токен и роль.

**Подключение (connection)** — локальная привязка пространства к папке хранилища. В одном хранилище может быть несколько подключений к разным пространствам. Плагин ведёт их список.

**Роли**

| Роль | Права |
|---|---|
| `owner` | чтение, запись, управление участниками и инвайтами |
| `rw` | чтение и запись |
| `ro` | только чтение |

Права выдаются на пространство целиком. Права на отдельные папки внутри пространства невозможны в принципе: сервер не знает путей. Разный доступ разным людям решается разными пространствами.

**Вход участника состоит из двух секретов:**

1. Код подключения `vw1:<base64url>` с полями `{ u: URL сервера, s: spaceId, i: инвайт }`. Выдаёт владелец.
2. Пароль шифрования, общий на команду, передаётся вне плагина.

## 2. Криптосхема

Всё на WebCrypto, доступном и на мобильных платформах. Node-crypto не используется нигде, `isDesktopOnly` остаётся `false`.

```
master     = PBKDF2-SHA256(password, salt, 650000, 32 байта)
contentKey = HKDF-SHA256(master, info = "vw:content:v1:<epoch>")   AES-256-GCM
metaKey    = HKDF-SHA256(master, info = "vw:meta:v1:<epoch>")      AES-256-GCM
pathKey    = HKDF-SHA256(master, info = "vw:path:v1:<epoch>")      HMAC-SHA256
```

Соль случайная, 32 байта, генерируется при создании пространства, хранится на сервере открыто.

**Адресация**

```
docId = base64url(HMAC-SHA256(pathKey, NFC(относительный путь внутри подключения)))
```

Детерминированная: два клиента независимо адресуют один файл без координации. Нормализация NFC обязательна, иначе кириллица с iOS (NFD) и с Windows (NFC) даст два разных документа для одного файла.

Разделители пути всегда `/`. Путь считается от корня подключения, не от корня хранилища: это позволяет разным участникам монтировать пространство в разные локальные папки.

**Шифрование записи**

```
metaCipher = AES-GCM(metaKey, JSON {
  path, mtime, ctime, size, plainSha256, deviceLabel, op
})
body       = AES-GCM(contentKey, содержимое файла)
```

У каждого шифроблоба свой случайный IV, 12 байт, префиксом к шифротексту. Дедупликация одинакового содержимого между участниками невозможна, это осознанная цена шифрования.

**Верификатор пароля**

При создании пространства владелец кладёт `verifier = AES-GCM(metaKey, "vaultwire-v1:" + spaceId)`. Каждый новый участник после ввода пароля обязан его расшифровать и сверить. Не сошлось — синхронизация не стартует и не пишет ничего. Без этой проверки один человек с опечаткой зальёт в пространство параллельный набор нечитаемых файлов.

**Хранение пароля на устройстве**

Опция подключения «запомнить пароль на этом устройстве», включённая по умолчанию: без неё окно разблокировки открывается при каждом запуске Obsidian, что слишком дорого по UX, особенно на мобильных устройствах. Подключение с сохранённым паролем поднимается автоматически, окно остаётся только для тех, у кого пароля нет. Не подошедший сохранённый пароль стирается, и окно открывается с объяснением.

При включённой опции пароль хранится в открытом виде в `data.json` плагина внутри хранилища, поэтому папку конфигурации Obsidian нельзя синхронизировать сторонними средствами. Самодельного шифрования поверх нет сознательно: ключ для него пришлось бы держать рядом, в том же файле, и защита была бы ложной. Выключение опции стирает сохранённый пароль немедленно.

**Ротация**

Поле `epoch` заложено в схему и участвует в выводе ключей. Процедура перешифровки пространства при смене пароля в v1 не реализуется, добавляется позже без миграции данных.

## 3. Протокол HTTP

Все клиентские запросы идут через `requestUrl` из API Obsidian: он не подчиняется CORS и одинаково работает на десктопе и на мобильных устройствах.

Аутентификация: `Authorization: Bearer <deviceToken>`.

```
POST   /v1/spaces                            bootstrap-токен
       → { spaceId, ownerToken, salt }
POST   /v1/spaces/{id}/devices               { invite, label }
       → { deviceId, deviceToken, salt, verifier, epoch, role }
GET    /v1/spaces/{id}
       → { seq, role, docCount, bytes, epoch, salt, verifier, retentionDays }
GET    /v1/spaces/{id}/changes?since=&limit=
       → { seq, items: [{ docId, rev, seq, deleted, metaCipher, blobHash, size }] }
POST   /v1/spaces/{id}/blobs                 сырое тело, заголовок X-Blob-Sha256
       → { hash, size }            201 новый, 200 уже был
GET    /v1/spaces/{id}/blobs/{hash}          → сырое тело
PUT    /v1/spaces/{id}/docs/{docId}          If-Match: <rev> | If-None-Match: *
       { metaCipher, blobHash, size } → { rev, seq }
POST   /v1/spaces/{id}/docs:batch            до 50 документов, тела ≤ 256 КБ
       → [{ docId, rev, seq } | { docId, error }]
POST   /v1/spaces/{id}/moves                 атомарный переезд
       { fromDocId, fromRev, toDocId, metaCipher, blobHash } → { rev, seq }
DELETE /v1/spaces/{id}/docs/{docId}          If-Match: <rev> → { rev, seq }
GET    /v1/spaces/{id}/docs/{docId}/revisions
       → [{ rev, seq, metaCipher, blobHash, createdAt }]
POST   /v1/spaces/{id}/invites               owner
       { role, expiresIn, maxUses } → { code, expiresAt }
GET    /v1/spaces/{id}/devices               owner
POST   /v1/spaces/{id}/devices/{did}/revoke  owner
```

`changes` отдаёт метаданные без тел: это позволяет построить полную картину и показать план до скачивания.

Тела и метаданные разнесены сознательно. Собирать multipart поверх `requestUrl` неудобно, поэтому тело заливается отдельным запросом и адресуется хешем, а `PUT /docs` остаётся чистым JSON.

**Коды ответов**

| Код | Значение | Поведение клиента |
|---|---|---|
| 401 | токен отозван или неверен | стоп подключения, баннер |
| 403 | роль не позволяет | не повторять, запись в журнал |
| 409 | рассинхрон `rev` | подтянуть документ, разрешить конфликт, записать снова |
| 413 | превышен лимит размера | пропустить файл, запись в панель |
| 429 | rate limit | откат по `Retry-After` |
| 5xx | сбой сервера | экспоненциальный откат, до 5 попыток |

Слепой повтор после 409 запрещён.

## 4. WebSocket

`wss://<host>/v1/sync`. Токен уходит первым фреймом после открытия, а не в query, чтобы не оседать в логах nginx.

Сервер шлёт `{ type: "changed", spaceId, seq }` всем устройствам пространства **после** коммита транзакции, кроме автора изменения. Данные всегда тянутся по HTTP, WebSocket служит только звоночком. Если соединение не поднялось, всё работает на интервальном опросе `changes`, по умолчанию раз в 30 секунд.

Heartbeat каждые 30 секунд обязателен: nginx и мобильные операторы рвут простаивающие соединения тихо. Нет ответа 60 секунд — переподключение с экспоненциальным откатом.

## 5. Сервер

Fastify, Prisma, PostgreSQL, Node 22, рантайм tsx.

```
Space    id, salt, verifier, keyEpoch, seq, retentionDays, maxRevisions, quotaBytes
Device   id, spaceId, tokenHash, role, label, lastSeenAt, revokedAt
Invite   id, spaceId, codeHash, role, expiresAt, maxUses, usedCount, createdBy
Doc      (spaceId, docId) PK, rev, seq, deleted, epoch, metaCipher, blobHash, size, deviceId
DocRev   spaceId, docId, rev, seq, deleted, metaCipher, blobHash, deviceId, createdAt
Blob     (spaceId, hash) PK, size, refCount
```

Индекс `(spaceId, seq)` обязателен: весь опрос изменений это `WHERE spaceId = ? AND seq > ? ORDER BY seq LIMIT ?`.

Токены и коды инвайтов хранятся только хешами SHA-256. Токен показывается один раз, при активации инвайта.

**Транзакция записи**: блокировка строки пространства, инкремент `seq`, upsert `Doc`, вставка `DocRev` — одной транзакцией. Это сериализует записи внутри пространства и исключает дырки в нумерации, из-за которых опрос молча пропускает изменения.

**Хранение тел**: файловая система, `blobs/<spaceId>/<хеш[0:2]>/<хеш>`. Шардинг по двум символам обязателен. Запись во временный файл и rename. Сервер сам пересчитывает SHA-256 принятого тела и сверяет с заголовком. Счётчик ссылок уменьшается при удалении, физическое удаление делает сборщик мусора после срока хранения и только когда на тело не ссылается ни одна ревизия. Слой хранилища скрыт за интерфейсом, чтобы позже подставить S3.

**Квоты**: лимит объёма на пространство и лимит размера одного тела. Rate limit по устройству, отдельный жёсткий по IP на активацию инвайтов.

**Аутентификация**: проверка по хешу токена, кэш проверенных токенов в памяти на 60 секунд, отзыв чистит кэш немедленно.

**Развёртывание**: `obsidian.boostix.space`, nginx на отдельный порт, pm2, деплой через GitHub Actions на self-hosted runner. Отдельная база данных, не схема внутри базы boostix. В nginx обязательны `client_max_body_size` под лимит вложения и заголовки Upgrade/Connection с `proxy_read_timeout 3600s` для WebSocket.

**Бэкапы**: ежедневный pg_dump и rsync директории тел, в порядке «сначала тела, потом база», чтобы база никогда не ссылалась на отсутствующее тело.

## 6. Клиентский движок

### Локальное состояние

Индекс подключения лежит в `<configDir>/plugins/vaultwire/state-<spaceId>.json`, пишется атомарно (временный файл и rename) с дебаунсом. Запись на файл:

```
{ path, docId, rev, plainHash, mtime, size, syncedAt, dirty }
```

`plainHash` — SHA-256 содержимого на момент последней успешной синхронизации, опорная точка сравнения.

### Трёхстороннее сравнение

| Локально | На сервере | Действие |
|---|---|---|
| без изменений | без изменений | ничего |
| изменено | без изменений | отправить |
| без изменений | изменено | принять |
| изменено | изменено | конфликт |
| удалено | без изменений | отправить удаление |
| без изменений | удалено | удалить локально в корзину |
| удалено | изменено | принять, файл воскресает |
| изменено | удалено | отправить, файл воскресает, запись в панель |
| создано локально | нет | отправить создание |
| нет | создано на сервере | принять создание |
| создано локально | создано на сервере | конфликт |

Локальное удаление всегда через `fileManager.trashFile`, никогда через `vault.delete`.

### Защита от массовых операций

Если прогон собирается удалить больше 20 файлов или больше 15 процентов подключённой папки, синхронизация останавливается и требует подтверждения со списком. Ловит отвалившийся сетевой диск и случайное удаление папки.

### Детект локальных изменений

События `vault.on('create'|'modify'|'delete'|'rename')`, зарегистрированные внутри `workspace.onLayoutReady()`. Плюс полный сверочный скан при запуске и по кнопке: он ловит изменения, сделанные при закрытом Obsidian, и является основным механизмом на мобильных устройствах, где фонового процесса нет.

Дебаунс на файл 300 миллисекунд. Obsidian сам сохраняет файл примерно через 2 секунды бездействия, поэтому больший дебаунс делает синхронизацию вялой без всякой пользы. Ожидаемая задержка от последнего символа до появления у другого участника: 2.5–3.5 секунды.

### Подавление эха

Перед записью принятого файла его путь добавляется в набор применяемых, запись идёт с `mtime` из метаданных, флаг снимается после события `modify`. Второй барьер: перед отправкой хеш сверяется с индексом, совпал — значит это наша собственная запись. Обе защиты обязательны: события асинхронны и одиночный флаг даёт бесконечный цикл отправки и приёма.

### Очереди

Отдельные очереди приёма и отправки, ограниченная конкурентность (4 на десктопе, 2 на мобильных), повторы с экспоненциальным откатом, максимум 5 попыток, дальше документ уходит в список проблемных с кнопкой повтора. В пределах прогона сначала применяются создания и обновления, затем удаления.

Переименование отправляется одним запросом `POST /moves`, а не парой удаления и создания: пара даёт окно, в котором другой участник увидит файл исчезнувшим и удалит его у себя.

### Стартовая последовательность

`onLayoutReady` → загрузка индекса и ключей → проверка верификатора → `GET /spaces/{id}` и сверка эпохи → локальный скан → `GET /changes?since=lastSeq` → сведение таблицы решений → применение (с предпросмотром, если операций больше ста или это первое подключение) → открытие WebSocket.

### Пределы

Файлы больше лимита (50 МБ на десктопе, 20 МБ на мобильных, настраивается) пропускаются с записью в панель. Разбиение файлов на части сознательно не делается.

## 7. Конфликты, история, корзина

**По умолчанию — конфликтная копия.** Серверная версия ложится в основной путь, локальная сохраняется рядом как `Заметка (конфликт, <устройство>, 2026-08-08 14-30).md`. Копия синхронизируется наравне со всем остальным, иначе автор не увидит её на своём втором устройстве. Есть команда «убрать все конфликтные копии подключения».

**Автослияние markdown — опция подключения.** Трёхстороннее построчное слияние. Базовый текст берётся с сервера: в индексе есть `rev` последней синхронизации, сервер хранит историю ревизий, поэтому локальное хранилище базовых копий не нужно.

Два жёстких ограничения: бинарные файлы всегда идут в конфликтную копию; если правки задели область frontmatter (определяется по `frontmatterPosition` из metadataCache), автослияние для файла отключается, потому что построчное слияние YAML порождает дубли ключей и ломает свойства незаметно.

Третья стратегия, «побеждает свежий», доступна в настройках подключения для служебных папок.

**История версий.** Последние 20 ревизий или 30 дней, что больше, настраивается на пространство. Панель истории файла показывает время, устройство и размер, позволяет посмотреть и восстановить. Восстановление создаёт новую ревизию, история не переписывается.

**Корзина.** Удаление это надгробие: документ помечен удалённым, тело живёт срок хранения. Панель корзины показывает что удалено, кем и когда, с кнопкой восстановления. Папка `.trash` внутри подключения жёстко исключена из синхронизации, иначе удалённые файлы возвращаются как новые.

## 8. Интерфейс плагина

Язык интерфейса русский. Все строки вынесены в отдельный модуль, чтобы позже добавить английский без раскопок по коду.

Разделение простое: **боковая панель это рабочее место, вкладка настроек это только настройки**. Панель открыта постоянно, и ходить за каждым действием в окно настроек слишком долго.

**Боковая панель**

Шапка: выбор активного подключения (при одном подключении просто его метка), состояние словами, время последнего успешного прогона, счётчики очереди и конфликтов, кнопки синхронизации, паузы, настроек подключения и отключения.

Пустое состояние: пояснение и две кнопки, «Подключить пространство» и «Создать пространство». Вторая всегда видима и гаснет без bootstrap-токена с объяснением, где он задаётся. Прятать её нельзя: исчезающее действие читается как поломка, а токен вводится в другом месте.

Вкладки относятся к активному подключению: активность (очередь, последние операции, проблемные документы), конфликты, корзина, участники (только у владельца). Внизу ссылка на настройки плагина.

Перерисовка точечная: шапка, полоса вкладок и активная вкладка обновляются раздельно, тело пересобирается только при смене вкладки или подключения.

**Вкладка настроек**

Список подключений только для чтения (метка, папка, роль, состояние) и кнопка «Открыть панель». Ниже: пределы (размер файла, конкурентность, период опроса), раздел «Сервер» с bootstrap-токеном, диагностика.

Настройки конкретного подключения открываются модальным окном из панели: фильтры включения и исключения, лимит размера, стратегия конфликтов, автосинхронизация, запоминание пароля.

**Мастер подключения**, три шага: код подключения, выбор локальной папки, пароль. Затем экран предпросмотра плана: сколько файлов придёт, сколько уйдёт, сколько конфликтов, объём. Применение только после подтверждения.

**Лента**: иконка открытия панели.

**Строка состояния**: иконка и состояние (ожидание, синхронизация, офлайн, ошибка, только чтение), клик открывает панель.

**Команды**: синхронизировать сейчас, открыть панель, показать конфликты, убрать конфликтные копии. Горячие клавиши по умолчанию не назначаются.

**Стиль**: DOM только через `createEl`/`createDiv`, никакого `innerHTML`. Ни одного литерального цвета, только переменные Obsidian. Все классы с префиксом `vw-`. Заголовки секций через `Setting.setHeading()`. Один управляющий элемент на строку настройки. Полный свод правил в `Плагин — стиль и правила приёмки` в хранилище boostix.

## 9. Ошибки и деградация

Классификация ошибок и реакция описаны в таблице кодов раздела 3. Сверх неё:

- **Офлайн**: изменения копятся локально с флагом `dirty`, отправляются при появлении сети. Работа в хранилище не блокируется никогда.
- **Неверный пароль или битый шифротекст**: подключение останавливается, показывается баннер, ничего не пишется ни локально, ни на сервер.
- **Отзыв устройства**: 401, баннер, подключение переходит в состояние «доступ отозван», данные на диске остаются нетронутыми.
- **Журнал**: кольцевой буфер на 500 записей в памяти плюс переключатель записи в файл для диагностики. Вывод в консоль в обычном режиме запрещён требованиями каталога.
- **Экспорт диагностики**: журнал, состояние подключений, версии, без секретов и без содержимого заметок.

## 10. Тестирование

**Криптомодуль**: фиксированные векторы вывода ключей, детерминизм `docId`, нормализация NFC, круговой тест шифрования и расшифровки, поведение при неверном ключе.

**Движок синхронизации**: чистые модульные тесты на таблицу решений с поддельными хранилищем и клиентом API. Покрываются все одиннадцать строк таблицы, пороги массовых операций, подавление эха, порядок применения. Это ядро корректности, покрытие обязательное.

**Сервер**: интеграционные тесты против реального PostgreSQL. Монотонность `seq` при параллельных записях, 409 при рассинхроне, атомарность переезда, сборка мусора тел, отзыв токена, квоты, лимиты запросов.

**Сквозные**: два экземпляра движка против реального сервера. Сценарии: одновременная правка одного файла, переезд файла, удаление, догон после офлайна, участник только для чтения, переподключение WebSocket.

**Ручные**: мобильный клиент через `app.emulateMobile(true)` и на реальном устройстве.

## 11. Структура репозитория и правила кода

```
plugin/    плагин Obsidian, TypeScript, esbuild, выход main.js
server/    Fastify, Prisma, PostgreSQL
shared/    типы протокола, схемы Zod, версия протокола
docs/      спецификации
```

Правила, одинаковые для всех частей:

- файл не длиннее 150 строк, одна ответственность на модуль;
- никаких `any`, вывод в консоль только через логгер;
- на сервере схемы Zod на теле всех изменяющих запросов;
- в плагине никаких Node и Electron API, `isDesktopOnly` остаётся `false`;
- общие типы протокола живут только в `shared/` и не дублируются.
